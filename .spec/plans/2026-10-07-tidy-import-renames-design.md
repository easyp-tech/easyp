# Checked import renames during mod tidy

User steering on 2026-10-07: `mod tidy` must update consumer imports when an updated dependency establishes a different root namespace. This extends the external-import-roots design. Its prohibition on automatic source changes continues to apply to get/update; tidy now has the explicitly requested source-editing responsibility.

## Contract

`mod tidy` resolves versions already declared in `protobuf.mod`; it does not upgrade dependencies by itself. When the previous lock and newly selected pinned dependency view prove a unique change of import name, tidy updates the relevant import declarations in the owning consumer module's `.proto` files. Root inference still uses only that dependency's own proto imports. Consumer edits cannot choose or override dependency roots.

Fetch and verify the old exact commit, effective roots and original hash before trusting a rename. Verify the new selected commit, metadata, roots and complete hash separately. An existing same pin retains its namespace unless an explicit resolution hint changes it. Native/Buf/legacy roots remain authoritative. An unrecorded metadata-free default `.` remains a fallback choice.

Use verified exported-name/source-identity maps for each old/new dependency, not only sets of names. If the old physical source is still uniquely exported in its dependency, preserve its binding: rewrite to its new name even when another source now occupies the original name. Strip only the commit prefix from identities when comparing pinned physical paths. Multiple current names for that old source are ambiguous unless its original name still binds to that same source. A name newly owned by a different dependency must never silently replace the old binding.

Retain an unchanged name when it still belongs to the same producer and no surviving old source contradicts that binding. This preserves ordinary contract evolution and physical moves that retain their public import names. If a needed old name disappears or belongs to another producer, accept only a unique verified source mapping; otherwise report the file, dependency revisions, roots and next actions. Never use a filename basename, protobuf package, consumer spelling or iteration order as a rename heuristic. Unused old files do not force edits or invalidate a valid new graph. Cross-dependency import collisions remain errors.

Only edit consumer files owned by the selected module and its declared roots, through the existing bounded source traversal. Exclude dependencies, caches, hidden/vendor/nested modules and separate workspace modules according to established ownership boundaries; do not add build-directory or gitignore heuristics. A build copy within an owned root remains an owned source unless existing boundaries exclude it. Internal aliases may address the same owned physical file: plan one write to the verified in-module target while preserving aliases. Outside ownership-boundary/unsupported links fail before writing, using existing sourceview rules. Local replace keeps its existing ephemeral graph behavior and does not rewrite source or shared lock as part of this first feature.

Parse protobuf import declarations, including `public`/`weak`, comments, escaped strings and concatenated literals. Replace only their literal tokens, preserving interleaved comments and whitespace. A concatenated declaration can encode the new path in its first literal and replace remaining literal values with empty strings while retaining their separators/comments. Preserve all other bytes, line endings, indentation and permissions. Identical strings in options/messages/comments must stay untouched. No environment expansion or full-file reformatting.

Prepare edits in memory. Resolve the verified new graph before the ordinary unresolved-import gate, then validate proposed consumer imports. Compile each changed consumer source and its reachable closure directly through the existing protocompile with a proposed-byte SourceRoots accessor before any project write. Do not introduce a whole-module duplicate-symbol check across independent targets or build copies. Unrelated dependency bodies retain existing reachability behavior. Runs with no source edits keep the existing tidy validation contract. Feed manifest augmentation/direct-indirect promotion the proposed imports or verified imported-owner set, rather than reread stale source bytes against new roots. A failure in pin/hash/root/import/symbol/compile validation keeps all project source, manifest and lock bytes intact.

Commit proposed source edits, comment-preserving manifest changes and the new lock through one staged file transaction with state rechecks and rollback for ordinary write/rename failures. Extend the existing `writeV1ResolvedFiles` path in `internal/modules/project_files.go`, which currently writes manifest/lock with rollback using `disk.WriteAtomicFile`; route its writes through the new staged helper rather than leave two competing module writers. Capture source and metadata existence/bytes/modes/physical identities/alias traces, including unchanged validation inputs. Stage bounded root-relative writes, then recheck before commit. Preserve recovery copies if rollback fails. Preserve verified internal source/metadata aliases, permissions and error causes. Multiple renames are not crash atomic; retain the existing documented project transaction limitation. Install/cache side effects may remain, but no producer source or cached files are modified.

The CLI reports applied file/import renames only after successful commit, in deterministic order. It also explains that generation selectors and SDK paths should be reviewed when the namespace changes. Library code returns structured results, without printing. Keep `Tidy(ctx, root, repository) error` available; a reporting variant can serve the CLI. Update/get keep their namespace-transition diagnostics and can point users to change the manifest requirement then run tidy. Frozen tidy remains rejected before source access or writes.

## Verification

Real Git cases: fallback `api/service/v1` to authoritative `api`; omitted default `.` to explicit producer root; unique inference remains independent of consumers; explicit already-adapted imports need no rewrite; unchanged pins stay fixed; physical move with same namespace passes; a new source reusing the old import name cannot hide a surviving source's unique rename; cross-dependency name reuse cannot rebind an old import; missing/ambiguous source identities fail unchanged; wrong old hash and moved tags still fail; multiple dependencies/roots and import collisions remain safe. A rewritten import of a transitive module promotes its requirement to direct while preserving manifest comments.

Edit cases: ordinary/public/weak imports; escaped and concatenated literals; inline/block comments; CRLF; identical non-import strings; duplicate declarations and alias paths; nested/workspace boundaries; owned build copies participate while copies outside established ownership remain untouched; modes preserved. Compile failure, source change between planning/commit and staged rename failure must roll back sources and metadata together.

Build fresh CLI/MCP with Go 1.26.6 and existing dependencies. Standalone v1 tests must observe actual source edits, deterministic CLI messages, unchanged dependency trees, cold-cache/frozen replay, generated SDK names and compilation. Docs cover the manifest-update/tidy flow and ambiguity diagnostics. No release tags are part of this change.
