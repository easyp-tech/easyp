# lint-easypc-infra — Requirements

**Status:** In Review
**Author:** agent (interview: пользователь)
**Date:** 2026-11-17

## Обзор

Линтер `easyp lint` переводится с go-protoparser на собственный компилятор
`easyp-protoc` (вендорится как `internal/easypc`) и модель `protoast`.
Эталонная реализация — проверенная в `easyp-tech/compiler-lab` (ветка
`easyp-cli`). Цели: производительность (не медленнее main, в лаборатории
20 мин → 0.08 с на `compute.proto`), buf-совместимое поведение на
некомпилирующихся файлах, три новых правила. Остальные подсистемы
(breaking, generate, `mod tidy`, `migrate`) не затрагиваются.

## Глоссарий

| Термин | Определение | Code Artifact |
|--------|--------------|---------------|
| `easypc` | Вендоренный в репозиторий компилятор `easyp-protoc` | `internal/easypc` |
| `protoast` | Модель файла для линтера поверх синтаксических деревьев `easypc` | `internal/protoast` |
| COMPILE issue | Замечание с именем правила `COMPILE` об ошибке компиляции файла | `internal/core/link.go` (лаборатория) |
| Корпус | Приёмочный набор proto-файлов: `api-common` (92), `googleapis-nocompute` (7414) | `compiler-lab/bench/projects` |
| Лабораторный CLI | Версия CLI из `compiler-lab/easyp-cli`, эталон для новых правил | `compiler-lab/easyp-cli` |
| Паритет | Полное совпадение множества lint-замечаний (правило, файл, строка, колонка) двух версий на корпусе | — |

## User Stories

- Как **разработчик proto-файлов**, я хочу, чтобы lint на больших корпусах
  (тысячи файлов) выполнялся не медленнее текущего, чтобы проверка не тормозила
  CI.
- Как **пользователь easyp**, я хочу buf-совместимую диагностику
  некомпилирующихся файлов (COMPILE), чтобы ошибки импортов и типов
  находились тем же запуском lint.
- Как **пользователь easyp**, я хочу неизменный формат вывода и коды выхода,
  чтобы существующие скрипты и CI продолжили работать без правок.

## Требования

### Группа 1 — Вендоринг компилятора

**REQ-1.1** WHEN исходники фичи собраны, the system SHALL содержать `easypc`
(компилятор целиком, включая `cmd/` и `testdata/`) и `protoast`, вкопированные
из `compiler-lab/easyp-cli` с импортами на `github.com/easyp-tech/easyp/internal/...`.

**REQ-1.2** WHEN выполнен `go mod tidy`, the system SHALL не содержать новых
внешних зависимостей для компилятора (без внешнего модуля и без `replace`).

### Группа 2 — Движок lint

**REQ-2.1** WHEN `easyp lint` запущен на компилирующемся корпусе, the system
SHALL построить модель каждого файла из слинкованных синтаксических деревьев
`easypc` и выполнить все применимые правила без изменения порядка обхода
файлов.

**REQ-2.2** WHEN хотя бы один файл корпуса не проходит линковку (ошибки
компиляции, не связанные с отсутствующим импортом), the system SHALL выдать
для этих файлов замечания с именем правила `COMPILE` (позиция и сообщение
компилятора) и не запускать правила на корпусе.

**REQ-2.3** WHEN линковка невозможна из-за отсутствующего импорта, the system
SHALL вернуться к разбору каждого файла по отдельности и репортить ошибку
чтения/синтаксиса как до этого изменения (без COMPILE issues).

**REQ-2.4** WHEN файл содержит ошибки чтения или синтаксиса, the system
SHALL вернуть ошибку выполнения команды для этого файла как до изменения.

**REQ-2.5** WHEN правило включено и файл попадает под `ignore`/`ignore_only`
или подавление комментариями (`allowCommentIgnores`), the system SHALL
применять те же правила подавления, что и текущий main.

**REQ-2.6** WHEN конфигурация lint содержит неизвестное имя правила или
группы в `lint.use`, the system SHALL вернуть ошибку валидации как до
изменения.

### Группа 3 — Паритет текущих правил

**REQ-3.1** WHEN `easyp lint` (новая реализация) и текущий main запущены на
корпусе `api-common` и `googleapis-nocompute` (все файлы компилируются),
the system SHALL выдать идентичное множество замечаний для всех 43 текущих
правил (правило, файл, строка, колонка).

**REQ-3.2** WHEN правило текущего main имеет поведение, изменённое в main
после снятия лабораторной копии (например, подавления через комментарии),
the system SHALL сохранить семантику текущего main, а не лабораторной копии.

### Группа 4 — Новые правила

**REQ-4.1** WHEN lint выполняется с группой `MINIMAL`, the system SHALL
включать правило `PACKAGE_NO_IMPORT_CYCLE`; WHEN с группой `BASIC`, the system
SHALL включать `SYNTAX_SPECIFIED` и `FIELD_NOT_REQUIRED` (размещение как в
лабораторном CLI).

**REQ-4.2** WHEN новые правила запущены на корпусах, the system SHALL выдавать
замечания, идентичные выводу лабораторного CLI на тех же корпусах.

**REQ-4.3** WHEN генерируются JSON-схемы конфигурации, the system SHALL
включать имена новых правил и групп в enum значений `lint.use`
(`task schema:generate`), и MCP-описания `mcp/easypconfig` SHALL отражать
обновлённый набор.

### Группа 5 — Совместимость

**REQ-5.1** WHEN `easyp lint` выдаёт замечания, the system SHALL сохранять
текущий формат вывода issues, пути и коды выхода CLI без изменений
(включая появление новых `COMPILE` в существующем формате).

**REQ-5.2** WHEN выполнены команды breaking-проверки, generate, `mod tidy`
и `migrate`, the system SHALL работать как до изменения (старая модель
go-protoparser для breaking сохраняется; `go-protoparser` и `protocompile`
остаются в `go.mod`).

### Группа 6 — Производительность

**REQ-6.1** WHEN `easyp lint` запущен на корпусе `googleapis-nocompute`,
the system SHALL завершаться не медленнее текущего main (потенциальный
выигрыш — как в лаборатории — не является требованием, только ориентиром).

## Топологический порядок

```
REQ-1.1, REQ-1.2 → REQ-2.1–2.6 → REQ-3.1, REQ-3.2 → REQ-4.1–4.3 → REQ-5.1, REQ-5.2, REQ-6.1
```
Причина: модель и движок (группа 2) требуют вкопированного компилятора
(группа 1); паритет правил (группа 3) проверяем только на новом движке; новые
правила и обновление схем (группа 4) — после стабилизации паритета;
совместимость и производительность (группа 5–6) — финальная приёмка на полном
наборе.

## Открытые design-вопросы

| Вопрос | Почему важен | Затронутые требования |
|--------|--------------|----------------------|
| Переключать lint-путь одним изменением (модель+движок+правила) или через временный мост старой/новой модели? | Определяет размер и ревьюемость диффа, риск долгоживущего дублирования | REQ-2.1, REQ-3.1 |
| Как фиксировать паритет: паритетные тесты на каждый батч правил против старой реализации или только корпусный lint-diff на финише? | Корпусный прогон не локализирует регрессию по правилу | REQ-3.1, REQ-4.2 |
| В каких батчах переносить 43 правила и в каком порядке? | Определяет план задач и точки проверки | REQ-3.1 |
| Переносить ли лабораторные `lint_helpers.go`/`casing.go` целиком или только используемое линтером подмножество? | Объём вендоринга vs удобство будущего синка с компилятором | REQ-1.1 |
